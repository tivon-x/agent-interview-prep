# Agent Notes

## Agent 有哪些特征

智能体AI 系统指的**是LLM在一个循环中运行的系统：它从环境中接收观测（用户消息、工具输出、传感器数据），对接下来该做什么进行推理，执行动作（工具调用、代码执行、API请求），并不断迭代，直到达成目标或显式请求人类介入。**这与“单轮聊天机器人”范式形成对比——后者只生成一次回复然后等待。

从聊天机器人到Agent 的转变带来了若干基本挑战，这些挑战是单次模型调用无法解决的：

- **持久性**：Agent 必须记住它做过什么、哪些尝试失败了、建立了哪些上下文——跨越多轮对话、多个会话，甚至数天。——短期记忆与长期记忆
- **Planning（规划）**：把复杂任务拆解成可执行的步骤序列。包括任务分解（Task Decomposition）、自我反思（Self-Reflection）、方案修正。
- **动作**：Agent 必须通过定义良好的接口与外部系统交互——数据库、API、文件系统、浏览器。
- **接地（Grounding）**：Agent 必须访问其训练数据中不存在的最新、特定领域的知识。
- **协作**：复杂任务往往超出单个Agent的能力范围；多个专门化的Agent必须协作、委派和协商。
- **安全性**：自主行动需要护栏、人类监督，并在Agent不确定时进行优雅降级。

## 长程 Agent 如何保持目标和执行路径稳定？什么时候应该 Replan？

现在模型自身的长程规划能力已经比较强，所以我不会一开始就设计很重的全局 Planner 和局部 Planner。更重要的是把**计划本身变成持久状态，而不是让模型每轮从对话历史里重新推断计划**。

比如我会维护 Goal、Todo、当前任务、已完成任务、失败尝试和剩余预算。正常情况下模型只推进当前 Todo，工具返回 observation 后做局部调整，不需要重新生成整个计划。

真正触发 Replan 的情况主要有三类：**原计划的关键假设失效、当前路径连续失败、用户目标发生变化**。

同时失败结果也要进入状态，例如某个方案为什么失败，避免模型过几轮之后再次尝试同一条路径。

所以现在防止路径震荡的重点已经不是“限制模型不能重新规划”，而是**稳定 Goal、持久化 Progress、记录 Failure，并让 Replan 事件驱动而不是每步驱动。**

---

在 Forge 里，我把长期目标和执行路径分开管理。**Goal 记录要达成什么**，持久化到 JSONL，并在每轮请求里重新注入目标和 ID；**Todo 记录当前怎么做**，由官方 Todo 中间件维护，可以随进展调整。所以 Todo 做完不等于 Goal 完成，必须核对验收条件后才能标记完成。

执行时，TaskCoordinator 会先提交阶段检查点，再派发任务；等待、完成和中止也有明确状态，恢复时按已保存的任务进度继续。

**是否 Replan 看新证据是否让当前路线失效。** 临时错误先重试；当前步骤的假设不成立，就局部调整；前置条件或整体约束变了，才重排后续计划。目标本身不清楚就暂停询问。Forge 只有在同一真实外部阻塞连续三轮后才标记 Goal blocked。

目前 Forge 已支持任务阶段的持久化与恢复；模型和工具执行本身的恢复还属于后续阶段，我不会把它说成已经完成。

## 如果模型特别擅长生成，但不擅长严格遵守流程，你会怎么把它放进一个强约束工作流里？

如果模型生成能力很强，但流程遵循能力一般，我不会只靠 Prompt，也不会简单把整个系统做成固定状态机。对于现在的 ReAct Agent，更合理的方式是把**决策权和执行权分开**：模型可以自主决定下一步做什么、调用哪个工具，但真正执行 Action 要经过 Harness。

第一层是限制 Action Space，用 Tool Schema、权限和动态 Tool 暴露限制模型能做什么；第二层是在工具调用前做 Precondition 和 Policy Check，比如测试没通过就不能发布；第三层是执行后的独立 Verification，不能让模型自己声明“完成”，而要通过测试、回读或者环境状态确认。

对于 Skill，我把它看成 soft constraint，它告诉 Agent 应该怎么做；真正不可跳过的步骤应该下沉成 Tool Guard、Hook、验收条件或者权限控制。像删除、转账、发布这类高风险 Action，还要加 Approval Gate。

同时 Runtime 维护显式状态、失败记录、重试次数和 Step Budget，避免死循环和路径震荡。

所以我不会说“系统控制整个流程、模型只负责局部生成”，那更像 Workflow。对于自主 Agent，更准确的是：

**模型控制执行路径，Harness 控制能力边界、关键状态和完成判定。**

这样既保留 ReAct Agent 的自主性，又保证关键约束不能被模型绕过。
