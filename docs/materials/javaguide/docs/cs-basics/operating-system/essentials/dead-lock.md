# 死锁

> 根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/cs-basics/operating-system/dead-lock.md) 整理；快照版本：`992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## 形成过程与必要条件

线程 A 持有锁 1 并等待锁 2，线程 B 持有锁 2 并等待锁 1；双方无法继续执行到释放锁的位置，等待关系形成闭环。死锁不一定表现为高 CPU，也可表现为线程阻塞、请求超时和队列堆积。

死锁发生必须同时满足四个条件：

| 条件 | 含义 |
| --- | --- |
| 互斥 | 某资源一次只能由一个执行单元占用 |
| 占有并等待 | 已持有资源，同时继续等待其他资源 |
| 非抢占 | 已分配资源不能被其他执行单元直接夺走 |
| 循环等待 | 等待关系形成闭环 |

四个条件是必要条件，并不表示列出四项就证明某个现场已经死锁。破坏任意一项可从结构上预防对应死锁；例如所有线程统一按锁 1、锁 2 的顺序获取，避免反向获取造成循环等待。

## 资源分配图与等待图

资源分配图中，执行单元指向资源表示请求，资源指向执行单元表示已分配：

- 图中无环，则没有死锁。
- 每类资源只有一个实例时，图中有环意味着死锁；某类资源有多个实例时，有环只说明可能死锁，还要判断是否存在能完成并释放资源的执行单元。

等待图只保留执行单元之间的等待关系。例如 `T1 → T2 → T1` 表示两个事务相互等待。数据库可在阻塞后检查等待图；内核 lockdep 则可根据锁获取顺序提示潜在环，两者发现问题的时机不同。

## 处理策略

| 策略 | 核心方法 | 限制 |
| --- | --- | --- |
| 预防 | 破坏四个必要条件之一，如固定资源获取顺序、一次申请所需资源 | 可能降低并发或需要提前知道资源集合 |
| 避免 | 分配前检查安全状态，例如银行家算法寻找安全序列 | 需提前知道最大需求，逐次检查有开销 |
| 检测 | 允许资源申请，检查是否形成等待环 | 需要维护和检查等待关系 |
| 恢复 | 终止、回滚或抢占，使等待链解除 | 可能丢弃工作；必须考虑状态一致性 |

银行家算法中，**安全状态**表示存在一个执行顺序，使各进程能依次获得剩余所需资源并完成；不安全状态不等于已经死锁，只是存在后续走向死锁的风险。

笔试计算时先求每个进程的 `Need = Max − Allocation`，再从当前可用资源 `Available` 中寻找一个 `Need ≤ Available` 的进程。假定它完成并释放已分配资源，把释放量加回 `Available`，继续寻找；所有进程都能完成，找到的顺序就是安全序列。检查新请求时，先确认请求不超过该进程的剩余需求和当前可用资源，再试分配并检查安全性；若不安全，撤销试分配，让申请方等待。

例如某种资源当前有 2 个可用，进程 A 已占用 1 个、还需 2 个，B 已占用 2 个、还需 3 个。A 可先完成并释放 1 个，此时有 3 个可用；B 随后完成，因此 `A → B` 是安全序列。多种资源时，比较和加减均按资源种类逐项进行。

工程上的预防通常包括统一加锁顺序、缩短持锁时间、避免持锁进行慢 I/O，拿不到全部锁时释放已有锁并按策略重试。`tryLock` 超时可限制等待，但需要处理失败、重试退避和幂等；否则可能变成频繁失败或活锁。不要随意强制停止持锁线程，线程可能已经修改了部分状态或产生外部副作用。

## 死锁、饥饿和活锁

| 情况 | 特征 | 常见原因 |
| --- | --- | --- |
| 死锁 | 等待关系闭环，相关执行单元无法继续 | 多锁反向获取 |
| 饥饿 | 系统整体仍有进展，某个执行单元长期拿不到资源 | 持续偏向高优先级任务或锁竞争不公平 |
| 活锁 | 执行单元持续运行、重试或相互让步，但没有完成任务 | 同步重试、缺乏合理退避 |

线程池或连接池耗尽、慢 SQL、外部服务超时、GC 停顿也会让请求卡住，不能仅凭线程等待或 CPU 低就认定死锁。

## Java 排查

可间隔一段时间连续采集线程栈，比较是否长期停在相同锁或业务代码：

```bash
jcmd <pid> Thread.print -l
jstack -l <pid>
```

`synchronized` 的栈信息可关注 `waiting to lock` 和 `locked`；`ReentrantLock` 等可关注 `parking to wait for` 和 `Locked ownable synchronizers`。沿“等待的锁 → 持有者 → 持有者正在等待的锁”寻找闭环，再回到代码检查锁顺序和持锁慢调用。

`ThreadMXBean.findDeadlockedThreads()` 可检查 JVM 可见的对象监视器和 ownable synchronizer，但无法单独还原横跨 JVM、数据库、远程服务的等待链。虚拟线程可用 `jcmd <pid> Thread.dump_to_file -format=text thread-dump.txt` 导出线程信息；其内容与传统线程 dump 并不完全相同，需结合日志及外部依赖状态。

## 数据库死锁

两个事务分别按 `1 → 2`、`2 → 1` 的顺序更新两行：若各自锁住第一行，再等待对方持有的第二行，就形成死锁。InnoDB 默认启用死锁检测，发现死锁后会回滚一个事务；PostgreSQL 也会检测并中止一个事务。应用应识别错误后按业务语义**重试整个事务**，并保证重试不会重复产生外部副作用。

降低风险可统一按主键等稳定顺序更新、缩短事务、检查索引和减少不必要的锁。MySQL 可用 `SHOW ENGINE INNODB STATUS` 查看最近一次 InnoDB 死锁；PostgreSQL 可结合日志、`pg_locks`、`pg_stat_activity` 与 `pg_blocking_pids()` 排查。跨 Java 锁和数据库锁时，应关联线程栈、数据库等待关系与业务日志。
