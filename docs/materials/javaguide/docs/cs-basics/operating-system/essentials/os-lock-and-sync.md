# 锁与同步机制

> 根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/cs-basics/operating-system/os-lock-and-sync.md) 整理；快照版本：`992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## 共享状态与临界区

临界区是访问共享可变状态、不能任意交错执行的代码。`count++` 通常包含读取、计算、写回，两个线程可能读到同一个旧值并覆盖彼此结果。锁保护的是**共同遵守的访问协议**：只要有一条访问路径绕过同一把锁，互斥就可能失效。

同步机制要考虑互斥与可见性，也要考虑进展、公平性和开销；临界区长度、竞争程度和调度环境都会影响选择。

| 机制 | 解决的问题 | 等待方式或边界 |
| --- | --- | --- |
| mutex（互斥锁） | 同一时刻只有一个持有者访问临界区 | 竞争时等待，实现可先短暂自旋再阻塞；通常由持有者释放 |
| spinlock（自旋锁） | 保护很短、不能睡眠的临界区 | 忙等，占用 CPU；持锁者被抢占或临界区较长时成本高 |
| semaphore（信号量） | 资源数量或并发许可 | 计数为 0 时等待；没有 mutex 那样的持有者语义 |
| condition variable（条件变量） | 等待共享状态满足条件 | 配合 mutex 原子释放锁并等待，返回前重新获得锁 |
| futex | 用户态同步器的阻塞和唤醒基础 | 无竞争通常只做用户态原子操作，竞争时进入内核等待 |
| 内存屏障 | 约束内存访问的顺序和可见性 | 本身通常不负责阻塞或互斥 |

## mutex 与自旋锁

mutex 用于保护共享结构，所有读写路径需遵守相同的加锁协议。锁内尽量只保留必要的状态变更，避免长时间等待网络、磁盘或外部服务。

自旋锁等待期间持续检查锁；多核上若持锁者很快释放，可能省去睡眠和唤醒开销。它适合非常短且不能睡眠的内核路径；单核或持锁者被抢占时，等待者持续占用 CPU 反而可能妨碍持锁者运行。业务代码一般优先使用成熟的同步原语，不手写忙等锁。

Linux 内核锁还受运行上下文约束：是否能睡眠、是否可能被中断重入、数据是否跨 CPU 共享。非 PREEMPT_RT 内核的普通 `spin_lock()` 会隐式禁止抢占，但不等于禁止硬中断；`spin_lock_irqsave()` 等接口才有相应中断处理。PREEMPT_RT 下 `spinlock_t` 语义不同，`raw_spinlock_t` 仍是严格自旋锁；不能把一种配置的结论套到另一种。

## 信号量与生产者、消费者

信号量维护非负计数：`sem_wait()` 在有许可时减 1，否则等待；`sem_post()` 加 1，并可能唤醒等待者。二值信号量可以模拟互斥，但信号量侧重许可数量，mutex 侧重临界区所有权。

有界缓冲区容量为 `N` 时：

1. `empty_slots` 初始为 `N`，`filled_slots` 初始为 0；另用 mutex 保护缓冲区结构。
2. 生产者等待一个空槽、加锁放入元素、解锁，再增加一个已填槽位。
3. 消费者等待一个已填槽位、加锁取出元素、解锁，再归还一个空槽。

信号量负责数量，mutex 负责对共享缓冲区的互斥修改。Linux 中 `sem_wait()` 可能因信号返回 `EINTR`，调用方需按策略处理或重试。

## 条件变量

消费者发现队列为空时，不能持锁睡眠，否则生产者无法获取锁并入队。条件变量与 mutex 配合，等待时原子地释放 mutex 并进入等待，唤醒返回前重新获取 mutex：

```c
pthread_mutex_lock(&mutex);
while (queue_empty(&queue)) {
    pthread_cond_wait(&not_empty, &mutex);
}
item = queue_pop(&queue);
pthread_mutex_unlock(&mutex);
```

生产者持相同 mutex 修改队列状态，再发通知。条件变量本身不保存状态，通知无人等待时不会变成之后可消费的许可；判断依据是受 mutex 保护的队列状态。等待必须使用 `while` 重新检查：可能出现虚假唤醒，也可能其他消费者先取走数据。同一条件变量存在等待者期间，POSIX 要求等待者使用同一把 mutex。

## futex 与原子操作

futex 的常见快路径在用户态通过原子操作更新 32 位锁字；竞争需要睡眠时执行 `FUTEX_WAIT`，释放后可用 `FUTEX_WAKE` 唤醒等待者。`FUTEX_WAIT` 在内核中原子地比较锁字与期望值并决定是否阻塞，避免检查后、睡眠前状态已变化造成的遗漏唤醒。应用通常使用 pthread 等更高层封装，而不是直接把 futex 当业务锁。

test-and-set、compare-and-swap（CAS）、fetch-and-add 等原子读改写，为锁建立不可拆分的起点。关中断只影响当前 CPU，不能单独实现多核共享数据的互斥。

## 内存顺序与优先级反转

锁还建立必要的内存同步：acquire 约束获取锁之后的访问不能移到获取之前；release 约束释放之前的访问不能移到释放之后。正确使用同一同步原语，后续持锁者才能按其语义观察先前释放者的写入。acquire/release 不是任意场景下的完整内存屏障。

优先级反转：低优先级线程 L 持锁，高优先级线程 H 等锁，中优先级线程 M 抢占 L，导致 H 间接受 M 阻碍。优先级继承让 L 临时继承等待者的较高优先级，尽快执行并释放锁。信号量缺少明确持有者，通常不能按同样方式进行优先级继承。
