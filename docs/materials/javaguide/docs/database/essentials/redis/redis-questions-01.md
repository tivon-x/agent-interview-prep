# Redis 常见面试题（上）

根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/redis/redis-questions-01.md)整理，快照版本 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## Redis 基础

### Redis 是什么，为什么快？

Redis 是以内存为主要数据存储介质的键值数据库，提供多种数据类型、过期、复制和可选持久化。访问内存、非阻塞网络 I/O 与事件循环、相对高效的数据结构可降低处理开销；具体吞吐取决于命令复杂度、网络、数据大小、磁盘、CPU 及部署。

与直接查数据库相比，缓存可降低读取延迟和数据库压力，但增加失效、一致性、网络和运维成本。与进程内本地缓存相比，Redis 可让多实例共享数据、集中管理；本地缓存访问无需网络但各实例状态独立。多级缓存需同时考虑各层失效。

### Redis 与 Memcached 的区别？

二者都可作为内存缓存。Redis 提供更丰富的数据结构、过期、复制和 RDB/AOF 等能力；Memcached 主要面向简单键值缓存。并发模型、持久化、部署和资源开销应按实际版本确认，不能只用单一吞吐数字比较。其他缓存方案包括 Caffeine 本地缓存和不同的分布式缓存服务。

### 常见缓存策略？

Cache Aside 由应用管理缓存与数据库；Read/Write Through 将回源和写入交给缓存层；Write Behind 异步写回。各自失败恢复与一致性边界见[缓存读写策略](./3-commonly-used-cache-read-and-write-strategies.md)。

### Redis Module 有什么用？

Redis Module 扩展服务器能力，可以引入新的数据类型和命令；部署时需确认模块版本、兼容性、资源开销和安全性。

## 应用与分布式协调

### Redis 除缓存还能做什么？

计数、限流、排行榜、会话、共享状态、分布式锁、消息传递、延时任务和地理位置查询。选择前应明确丢失窗口、数据规模、并发和恢复方式，不要将缓存服务自动视为可靠消息系统。

### 如何实现分布式锁？

- **获取**：用 `SET lock-key unique-token NX PX ttl` 原子设置唯一标识和过期时间。
- **释放**：用 Lua 原子比较 token 并删除，避免持有者超时后误删其他客户端的锁。
- **过期与故障**：业务执行超出租约时锁可能已归他人；还需处理续期失败、客户端暂停和故障切换。
- **外部资源**：严格排他需要资源端校验单调 fencing token，不能仅靠客户端认为自己仍持锁。

### 能否做消息队列和延时任务？

- **List**：可阻塞弹出，但需自行设计确认和失败恢复。
- **Pub/Sub**：向在线订阅者广播，不保存离线消息。
- **Stream**：支持消费组、待确认消息和重投，仍需考虑持久化、消费者崩溃及幂等。
- **延时任务**：可用有序集合存到期时间，或借助客户端延迟队列。过期事件在实际删除 key 时发出，可能延迟、丢失或被多个订阅者接收。

详见[消息队列](./redis-stream-mq.md)和[延时任务](./redis-delayed-task.md)。

## 数据类型与场景

| 类型 | 例子 | 注意 |
| --- | --- | --- |
| String | 缓存对象、计数器、分布式锁 | 二进制安全；整数命令原子操作；编码因值和版本变化 |
| Hash | 用户资料、购物车，按字段读取或增减 | 单个 key 可能变大变热；序列化 String 适合整体取写 |
| List | 队列、时间线 | 两端操作方便，可靠消费需额外确认和恢复机制 |
| Set | 标签、去重、共同关注、随机抽奖 | `SRANDMEMBER` 随机取样，`SPOP` 取样并移除；大集合运算可能耗时 |
| Sorted Set | 排行榜、按时间排序的待处理任务 | 成员唯一、按 score 排序；同分以成员字典序比较 |
| Bitmap | 用用户 ID 对应偏移，按日记录签到或活跃 | 稠密编号节省空间；极大稀疏偏移可能浪费内存 |
| HyperLogLog | 使用 `PFADD` / `PFCOUNT` 近似统计页面 UV | 估计值存在误差，不能列出元素，不适合精确计数 |
| GEO | 经纬度、范围查询 | 要区分球面距离与真实路程 |

String 内部使用动态字符串 SDS 或整数等编码，避免反复扫描字符串长度；具体编码取决于值与版本。购物车如果频繁单件修改，可用 Hash 字段；整体读写可用 String 序列化，结合 key 大小、并发、TTL 和业务原子性选择。

排行榜通过 `ZADD` / `ZINCRBY` 更新分数，`ZRANGE` 或排序相关命令取成员及排名。较大 Sorted Set 常结合哈希表与跳表：前者用于按成员定位，后者支持有序遍历和范围查询；较小集合可能采用紧凑编码。跳表实现和范围遍历较直观，不能因此断言所有场景都优于红黑树或 B+ 树。

判断元素肯定不存在可使用 Bloom Filter：判不存在通常可信，判存在可能是误报；实现和持久化取决于使用的模块或方案。位图、集合和 Bloom Filter 解决的问题不同，注意扩容、参数及误报率。

## 持久化

RDB 定期生成快照，可能损失最后一次快照后的写入；AOF 记录写命令，刷盘策略决定延迟与潜在丢失窗口。AOF 重写压缩重建所需内容，Redis 4 支持混合持久化，Redis 7 引入多文件 AOF。`fork`、写时复制和磁盘压力仍可能影响延迟；具体见[持久化](./redis-persistence.md)。

## 线程模型

传统 Redis 使用单个主线程执行多数命令，并通过事件循环处理网络事件；后台任务如持久化、异步释放可使用子进程或后台线程。单线程命令执行简化共享状态协调，但长命令会阻塞其他命令。Redis 6 引入可配置网络 I/O 多线程，主要并行处理网络读写等工作，不意味着所有命令执行都并行；不同版本实现和配置有差异。

过去网络可能不是主要瓶颈，单线程减少同步复杂度且内存操作快；高连接数或高吞吐时网络 I/O 也可能成为瓶颈，引入 I/O 线程用于分摊该部分工作。应结合 `INFO`、慢日志及系统指标定位瓶颈。

## 过期与内存淘汰

TTL 限制数据生命周期、降低陈旧数据残留并释放空间，但会增加回源。惰性删除在访问过期 key 时检查，主动过期周期性抽样清理，两者共同作用；到期时间不等于精确删除时刻。大量 key 同时到期会增加回源和清理压力，可结合 TTL 抖动、预热、限流与容量规划。

达到 `maxmemory` 时，策略决定能否淘汰及从哪些 key 中选择：

| 策略 | 行为 |
| --- | --- |
| `noeviction` | 不淘汰，拒绝会增加内存的写入 |
| `allkeys-lru` / `allkeys-lfu` / `allkeys-random` | 从全部 key 中按近似 LRU、近似 LFU 或随机方式选择 |
| `volatile-lru` / `volatile-lfu` / `volatile-random` / `volatile-ttl` | 只从设置过期时间的 key 中选择；候选不足时可能无法执行写入 |

TTL 到期删除和内存压力淘汰是两种不同机制。
