# Redis 持久化：RDB、AOF 与恢复

根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/redis/redis-persistence.md)整理，快照版本 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## RDB 快照

RDB 保存某一时刻的数据集，适合备份、复制和相对快速恢复；两次快照之间的写入在故障时可能丢失。`SAVE` 在主线程同步生成快照，会阻塞服务；`BGSAVE` 先 `fork` 子进程再由子进程生成，fork 本身仍可能造成停顿。

fork 使用写时复制（COW）：父子进程初始共享页面，快照期间父进程写入会产生页面副本。例如快照进行时修改很多原有数据，会产生额外物理页，峰值内存不等于数据集本身。fork 还需复制页表，数据量、页表、写入速率、可用内存和操作系统透明大页（THP）都会影响 fork 延迟及峰值内存。应预留 COW 内存、观察 fork 和快照耗时，并按环境评估 THP。快照文件生成成功后再替换旧文件，失败时需要检查日志和备份状态；异步快照不表示整个过程不存在主线程停顿。

## AOF 追加日志

Redis 执行写命令后记录可用于重建状态的命令，按配置追加和同步到文件。先执行再记录避免记录未通过检查的命令，但执行与持久化之间仍有故障窗口，不提供无条件零丢失。

| `appendfsync` | 行为与代价 |
| --- | --- |
| `always` | 每次写入后同步，丢失窗口较小但 I/O 延迟较高 |
| `everysec` | 通常每秒异步同步一次，故障时可能丢失约一秒数据，实际窗口受系统状态影响 |
| `no` | 交由操作系统决定刷盘时间，吞吐较好但丢失窗口不可控 |

AOF 的路径是执行命令、将相应记录追加到 AOF 缓冲区，再写入内核缓冲区并根据策略执行 `fsync`。`write` 返回不表示已经持久化到设备；即便使用 `fsync`，最终保证仍依赖操作系统和存储设备。`everysec` 下后台同步或磁盘繁忙也可能影响写入和尾延迟；约一秒是常见情形，不能把任何环境下的最大丢失窗口断言为固定秒数。

### 重写过程与失败边界

AOF 重写读取当前数据库状态，生成能重建该状态的更紧凑记录，不是逐条压缩旧 AOF。例如同一计数器多次递增可由当前最终值重建。`BGREWRITEAOF` 可手动触发；自动重写受 `auto-aof-rewrite-min-size` 和 `auto-aof-rewrite-percentage` 控制，是否触发取决于实际配置。

旧版重写期间，子进程生成新文件，父进程继续服务，并记录期间的增量；子进程完成后再结合增量并切换，不能丢掉快照期间的写。Redis 7 的 multipart AOF 将 base、incremental 和历史文件交由 manifest 组织：重写期间增量写入独立文件，成功后切换文件集合。具体恢复流程和配置依版本而定；原文将这一设计的背景归于[阿里开发者对 Redis 7 的介绍](https://mp.weixin.qq.com/s/RnoPPL7jiFSKkx3G4p57Pg)。

重写依赖 fork、COW 和磁盘空间，fork 失败、磁盘或 inode 耗尽、重写异常中断都需要告警和恢复处理。结合 `INFO persistence` 中重写进度、成功状态、文件大小、`aof_delayed_fsync`，以及 `df -h`、`df -i` 和系统磁盘延迟排查；具体字段和含义以运行版本为准。

## 完整性与混合持久化

纯 AOF 是命令日志，损坏时可能解析失败或尾部不完整；能否自动截断和恢复取决于故障位置、配置与版本。`aof-load-truncated` 控制符合条件的尾部截断是否允许继续启动；文件中间损坏不能简单当成尾部截断处理。不可把纯 AOF 当作每条命令都有校验和。`redis-check-aof` 修复可能从错误位置截断后续数据，应先保存原文件副本并确认文件集合及版本，再进行离线检查和恢复验证。

Redis 4 起支持 AOF 重写使用 RDB 格式前缀，后续记录增量 AOF；恢复先加载快照，再重放后续命令。`aof-use-rdb-preamble` 控制相关行为，默认值需核对版本。RDB 段的 CRC64 检查受 `rdbchecksum` 等配置影响；AOF 增量段仍需按其格式解析，不代表所有增量命令都具备独立校验和。Redis 7 多文件 AOF 下应完整保留 manifest、base 与所需增量文件，不可只复制一个文件就宣称可恢复。

## 选择和验证

RDB 更适合周期性快照和备份，AOF 可按刷盘策略缩小丢失窗口；同时开启时恢复优先级和配置以具体版本为准。持久化不替代异地备份、复制或恢复演练；监控 fork 时长、COW 内存、AOF 大小、重写状态、磁盘空间与延迟，并定期在隔离环境验证恢复。
