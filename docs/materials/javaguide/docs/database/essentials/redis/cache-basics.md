# 缓存基础：分类与一致性

根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/redis/cache-basics.md)整理，快照版本 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## 原理和选择

缓存将访问频繁、可复用的数据放在访问成本更低的位置，以减少数据库或远程服务压力。需要考虑数据更新频率、容量、淘汰、故障及允许的数据陈旧时间；读取后还能重建的数据更容易缓存。

| 类型 | 位置及优点 | 主要限制 |
| --- | --- | --- |
| 本地缓存 | 应用进程内，读取不需要网络，延迟低 | 容量受单机限制；多实例数据不自动同步，重启后可能丢失 |
| 分布式缓存 | 独立服务，如 Redis；多个实例共享 | 引入网络、部署、可用性和一致性开销 |
| 多级缓存 | 组合本地缓存和分布式缓存 | 减少远程访问，但同时维护多层失效和回填更复杂 |

Java 本地缓存可使用 Caffeine 等；分布式缓存常见 Redis、Memcached。它们的线程模型、数据类型、持久化能力和部署方式不同，应结合版本和场景选择。

`HashMap` 只是容器，不提供并发安全、容量淘汰或过期策略；`ConcurrentHashMap` 支持并发访问，也不自动提供完整缓存管理。Caffeine 等缓存库提供容量、过期和加载等机制，配置仍要贴合数据特点。多实例下轮询会让请求分散到不同进程，每台机器需各自预热；会话亲和可以提高部分命中率，但机器更替、扩缩容和热点倾斜会改变效果。

## 多级缓存一致性

写入后可发布失效通知让实例清理本地缓存，再由读请求重建；还应考虑消息丢失、服务离线、重启和重复通知。定时刷新或 TTL 可以兜底，但主动删除共享缓存后，本地缓存仍可能继续返回旧值，直到通知成功或刷新到期。不同层各自的 TTL 不能保证严格实时一致。

- Redis Pub/Sub 向在线订阅者广播，断线期间通知不会重放；可配合本地 TTL，连接状态不可信时清理本地缓存。
- Stream 或消息队列可以保留消息并重试，但同一消费组内的实例会分担消息，并非每台机器都收到每条失效；要让每份本地缓存失效需明确广播机制、各实例消费位置和保留时间。
- Redis Client Tracking 能通知 Redis key 的改变，但不能感知尚未同步到 Redis 的数据库更新；若失效先到而旧读取响应后到，还需防止迟到响应重新写入本地缓存。

只定时刷新而禁止请求回源时，写入后删除缓存可能使读端在下次刷新前拿不到数据；应提供可靠主动刷新、失败重试与降级。如果允许回源，应在多层均未命中时查询权威数据并重建，并对同一个热点合并并发加载。允许使用旧值时仍需设置最大陈旧期限。

需要更强一致性时，先定义权威数据源、可接受的陈旧范围、失败补偿与回源时序，再设计版本、失效和重试机制；单凭某一层缓存配置无法保证数据库与所有实例原子一致。
