# Redis 常见面试题（下）

根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/redis/redis-questions-02.md)整理，快照版本 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## 事务

### 如何使用事务和 WATCH？

`MULTI` 开始入队，`EXEC` 执行队列，`DISCARD` 取消。事务执行期间队列中的命令不会被其他客户端命令插入，但不等同于关系型数据库完整 ACID。

`WATCH` 监视 key：在 `EXEC` 前若 key 被修改，`EXEC` 中止，客户端可重读并重试。同一连接在事务外修改被监视 key 也会触发中止；事务内排队的修改则在 `EXEC` 检查通过后执行。

例如客户端 A 执行 `WATCH balance`、读取余额并进入 `MULTI` 后排队更新；客户端 B 在 A 的 `EXEC` 前修改了 `balance`，A 的 `EXEC` 不执行队列。A 必须重新读取和验证后再决定是否重试。

### 事务失败会回滚吗？

- **入队阶段**：语法等错误可能使整个事务不执行。
- **执行阶段**：某个命令失败不会自动回滚其他已执行命令。
- **持久性**：受 RDB/AOF 与刷盘策略影响，不能假定故障后事务一定持久。

Lua 可将读写逻辑放在服务端原子执行，但运行时错误也不自动回滚先前写入；需提前校验，并处理幂等、持久化与集群限制。

## 批量、pipeline 与 Lua

`MGET`、`MSET` 等原生批量命令减少往返；pipeline 批量发送命令再接收响应，降低 RTT，但各命令仍分别执行，不提供事务隔离。Lua 脚本可在服务端连续执行逻辑，适合比较并删除锁等操作；脚本过长会阻塞其他命令，且应避免将大量数据一次性加载到服务端。Redis Cluster 的多 key 命令 / 脚本通常要求相关 key 位于同一 hash slot。

## 大 key 与热 key

大 key 指单个值很大或集合元素很多：读取、复制、删除可能带来主线程处理、网络、内存和迁移压力。形成原因包括无限增长的集合、过期策略缺失和未分页聚合。可用 `SCAN` 配合类型与大小检查、`redis-cli --bigkeys` 等定位，注意采样不一定发现全部问题；将数据按业务分片、限制大小、分批处理，删除可视版本使用 `UNLINK`。

热 key 指访问频率极高的单个 key，可能造成节点 CPU、网络饱和；可结合服务侧指标、采样、`redis-cli --hotkeys`（受 LFU 配置等条件限制）定位。应对方式包括本地缓存、多副本读、热点拆分、请求合并和限流；副本滞后、本地缓存一致性和拆分聚合会增加复杂度。

慢查询可能由大集合、高复杂度命令、昂贵脚本等引起。使用 `SLOWLOG` 分析命令执行耗时，结合端到端延迟、网络和系统指标；慢日志并不覆盖客户端排队及全部 I/O 时间。内存碎片的检查和整理见[内存碎片](./redis-memory-fragmentation.md)。

## 缓存异常

| 问题 | 触发条件 | 常用处理 |
| --- | --- | --- |
| 穿透 | 请求不存在的数据，缓存未命中后反复访问数据库 | 对无效参数做校验；短 TTL 缓存空结果；Bloom Filter 过滤明显不存在的数据；限制滥用 |
| 击穿 | 单个热点 key 过期或失效，大量请求同时回源 | 热点不过期并异步刷新、请求合并、互斥重建、限流；锁超时和重建失败需处理 |
| 雪崩 | 大量 key 同时失效，或缓存服务故障导致大批请求回源 | TTL 抖动、分批预热、多级缓存、熔断限流、容量冗余与故障演练 |

击穿通常针对单热点，雪崩涉及大批 key 或节点失效；穿透的关键是查询不存在的数据。空结果缓存要考虑新数据创建时失效；Bloom Filter 有误报且需可靠更新。预热可在启动或低峰按热点分批加载，限制速率并监控数据库压力；无法预知全部热点，需有正常回源路径。

大量 key 集中过期除引发数据库回源，还可能增加 Redis 主动清理负担。TTL 加随机扰动可降低同步过期概率，但不能替代对节点故障的降级和容量设计。

## 缓存与数据库一致性

常见 Cache Aside 写流程为提交数据库后删除缓存，读未命中时回源并填充；删除失败、旧事务 / 延迟从库读取、旧读在删除后回填都可能导致旧值。重试、事务消息表或 CDC 可处理失效任务丢失，TTL 与延迟双删只能减小部分风险。需要更强保证时应定义权威读路径、同步协议与失败恢复；Redis 与数据库不因一次 Lua 脚本而成为同一原子事务。

## 阻塞、集群与使用规范

慢命令、大 key 同步释放、`SAVE`、fork / COW、AOF 磁盘压力、swap、CPU 与网络竞争都可能引发延迟；见[阻塞排查](./redis-common-blocking-problems-summary.md)。复制、哨兵和分片集群的详细文章在该上游快照中属于付费入口，[集群来源说明](./redis-cluster.md)列出限制。

使用中应限制大 value 和大集合、避免线上阻塞全量扫描、使用合理 TTL 和 key 命名、监控内存与淘汰、为超时和缓存失效设置降级，并根据业务要求验证持久化与恢复。pipeline、事务及分布式锁的原子性范围应单独判断。
