# 三种缓存读写策略

根据 [JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/redis/3-commonly-used-cache-read-and-write-strategies.md)整理，快照版本 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

## Cache Aside（旁路缓存）

应用同时管理缓存和数据库。读时先查缓存，未命中则查数据库并回填；写时先提交数据库事务，再删除缓存，后续读请求按需重建。它适合读多写少且允许一定陈旧窗口的数据。

先删缓存再写数据库会使并发读把旧值重新写入缓存；先提交数据库再删除缓存也不能保证强一致：读请求可能在提交前读旧值，却在删除后才回填。读从库延迟、旧事务快照和删除失败也会造成陈旧值。删除比主动更新更易避免并发写乱序覆盖，但不能自动解决旧值回填。

删除失败可使用事务消息表或 CDC 衔接重试，监控失败和积压；TTL 限制部分陈旧窗口，但旧快照反复回填或续期可能延长陈旧时间。延迟双删只能降低部分风险，不能保证所有延迟都被覆盖；跨 Redis 和数据库的操作也不会因 Redis 锁或 Lua 自动变成一个事务。强一致需求需明确权威读路径和完整同步协议。

## Read/Write Through（读写穿透）

应用读写缓存服务，缓存层负责与数据库交互。Read Through 未命中时由缓存层回源并填充；Write Through 将写入同步传递给数据库，写入缓存和数据库的具体顺序与未命中处理取决于实现，成功条件也应明确。与 Cache Aside 相比，回源和填充责任从应用下沉到缓存服务。Redis 本身并不自动提供面向任意业务数据库的此类回源和同步，通常需中间层或业务代码实现。同步写增加延迟和耦合，仍需定义失败处理及一致性语义。

## Write Behind（异步写回）

应用先写缓存，缓存层异步批量写入数据库。合并写操作可降低写压力，但数据库短时间落后；缓存故障或写回失败可能丢失数据。需要处理持久化、队列积压、顺序、重试及恢复，不能当作默认强一致方案。
