# MySQL 索引原理与设计

来源：[JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/mysql/mysql-index.md)，快照 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

索引是帮助定位记录的额外数据结构，可减少需要读取的数据，也可能帮助排序、分组和覆盖查询；代价是存储、写入更新、页分裂和维护成本。是否使用由优化器根据数据分布、选择性和估计成本决定。

## 按约束和字段分类

主键索引要求键值唯一且非空，每张表只有一个主键；唯一索引约束键值唯一，但可空列的 `NULL` 处理依数据库规则。普通二级索引不要求值唯一。单列索引只有一个键列，联合索引包含多个键列；前缀索引只保留字符串的前一部分，可能存在更多重复且不能无条件替代完整列索引。全文索引适合分词搜索，空间索引服务空间数据，均有引擎、版本和查询方式限制。

## 为什么常用 B+ 树

B+ 树高度平衡、每页保存较多键，减少树高和随机 I/O；数据项位于叶子，叶子有序，便于范围扫描。普通 BST 可能退化成链表；AVL、红黑树均为二叉树，磁盘页利用率及树高通常不如多路 B+ 树。哈希结构适合等值查找但不天然支持有序范围扫描，哈希碰撞需要处理；InnoDB 自适应哈希是引擎按访问模式建立的辅助结构，不等于表上可手工创建的普通哈希索引。

## 聚簇、二级与覆盖

InnoDB 聚簇索引叶子保存完整行，主键通常是聚簇键；没有主键时选择合适的非空唯一键，否则生成隐藏行 ID。二级索引叶子包含索引列及主键值；查询所需列不在二级索引中时，通常依据主键回到聚簇索引取行，称为回表。

覆盖索引指所需列均能从选用的索引读取，通常减少回表。`SELECT *` 不是一定索引失效，但可能不再覆盖且回表成本高。长主键会增加二级索引条目体积；随机主键可能增加页分裂，具体影响取决于负载和数据分布。

例：表有主键 `id`、`name`、`age`，并有二级索引 `idx_name(name)`。`SELECT id, name FROM users WHERE name='Ada'` 需要的字段通常已在索引中；`SELECT age FROM users WHERE name='Ada'` 在该索引无法提供 age 时需要按 id 回表。是否选用该索引仍须看执行计划。

## 联合索引与下推

`(a,b,c)` 按列顺序建立有序键；连续前缀可支持对应等值和部分范围访问，也可能帮助排序。第一列缺失、范围条件之后的列、`LIKE` 前缀匹配等能否继续用于边界定位、排序或过滤，取决于谓词和优化器；不能把“遇到范围后其他列一律无用”当成通用规则。

索引条件下推（ICP）允许引擎先在索引记录上判断可下推的条件，再对符合条件的候选行回表；不等于覆盖索引。选择合适的等值、关联和排序列及顺序，结合查询模式、选择性、写入成本与 `EXPLAIN` 验证。前缀索引节省空间但可能降低区分度，也不一定满足覆盖和排序；避免冗余或低价值索引，并在确认业务影响后清理。

例如 `(a,b,c)` 上，`a=1 AND b=2` 有连续前缀；`a=1 AND c=3` 通常先按 a 缩小范围，c 是否在索引条件下推中参与过滤取决于计划；`b=2 AND c=3` 没有 a 前缀，但某些版本和条件可能选择 skip scan。SQL 中谓词书写顺序不决定联合索引列顺序。

对 `(zipcode,birthdate)`，查询邮编等值并筛选生日月份且需要其他列时，若计划支持 ICP，可先在索引中筛选生日，再回表取完整行，减少回表次数。`EXPLAIN` 的 `Using index condition` 可作为识别线索；函数能否下推需以具体版本和计划为准。

## 选型检查

优先考虑频繁过滤、连接和排序字段，结合区分度、字段长度、更新频率和排序方向；写热点列增加索引会放大写入成本。联合索引能否取代多个单列索引取决于实际查询和前缀；避免 `(a)` 与已有 `(a,b)` 盲目重复，但保留或删除之前仍需比较唯一性、长度、查询负载和线上计划。无论索引看上去如何合理，都需用实际基数与 `EXPLAIN` 验证。
