# MySQL 到 Elasticsearch 数据同步

来源：[JavaGuide 原文](https://github.com/Snailclimb/JavaGuide/blob/992dae31eade2a34ba8dbbbcf5ed9de5511325ec/docs/database/mysql/mysql-to-elasticsearch-sync.md)，快照 `992dae31eade2a34ba8dbbbcf5ed9de5511325ec`。

同步前明确：MySQL 是事实源还是双向写入、可接受延迟、丢失与重复的处理、删除语义、重建能力及对账方式。MySQL 提交和 ES 索引刷新分属不同系统，不能仅凭“双写成功”保证原子一致。

| 方案 | 特点和代价 |
| --- | --- |
| 应用双写 | 简单但数据库提交、网络失败或 ES 写入之间存在缺口，需要重试及修复 |
| 本地消息表 / Outbox | 业务变更和消息写入同一数据库事务，异步投递；仍要实现去重、顺序、投递监控 |
| 定时全量/增量 | 简单但有延迟；增量需可靠水位、删除处理和重叠区间 |
| 基于 binlog 的 CDC | 捕获数据库变更并异步更新 ES；可用 Canal、Debezium、Flink CDC 等，需维护位点、日志保留与版本兼容 |

全量构建与增量捕获要建立一致的起始点，避免切换期间遗漏；新索引校验完成后可用别名切换，保留回滚方案。

## 定时增量与全量重建

用更新时间增量拉取时，任务开始固定 `cutoff`，按 `(updated_at,id)` 排序和记录复合游标；相同时间戳的多行不会因为只保存时间而被漏过。数据可能晚提交或时间戳异常时，还需要重叠窗口和幂等；物理删除不会留下更新时间，需删除日志、逻辑删除或定期全量校验。

全量重建先创建新索引及 mapping，导入、补齐重建期间的增量并校验，然后通过一次别名变更切换读流量，保留旧索引供回滚。别名切换本身不能补偿全量期间遗漏的写入。

## CDC 实现与交付边界

Canal 订阅 binlog 并交由客户端或 MQ 消费，通常还需要单独完成全量导入和位点衔接。Debezium MySQL Connector 常与 Kafka Connect 搭配，支持快照和后续 binlog，写 ES 仍需 sink 或消费者。Flink CDC 可分片读取增量快照并记录上下界位点、checkpoint 和之后的 binlog；具体锁行为及支持能力取决于连接器版本。

CDC 通常要求开启 binlog、按工具要求配置 ROW 格式、唯一 server ID、权限及足够的保留期；源切换时还要验证 GTID 和位点。Source 的 exactly-once 不自动等于 MySQL 到 ES 的端到端 exactly-once：Sink 可能重放请求，固定文档 ID 和幂等写入应对重复，版本策略应对乱序，删除事件也要纳入同一规则。

以稳定主键作为文档 ID，并设计幂等写入；重复投递、乱序、删除和多表聚合都需要明确处理，可用来源版本或业务版本拒绝过期事件。Bulk 请求成功不等于每项成功，逐项检查并重试可恢复错误。同步系统还要处理 mapping/DDL 变更、时间类型、失败队列、位点落后于 binlog 保留窗口、监控与告警；定期按业务口径对账并提供重建能力。

## 映射、失败和对账

- 同一文档按主键分区可降低乱序，但重试、重平衡或多条链路仍需单调版本；旧更新不能覆盖新版本，延迟的旧更新也不能复活已删除文档。
- `Bulk` 逐项区分临时错误和永久错误；429、部分 5xx 可按策略退避，mapping 冲突通常要修数据或映射并进入失败处理，避免无限重试和无界内存队列。
- 金额应约定最小单位或精度，`BIGINT UNSIGNED` 可能超出 ES `long` 范围；区分缺失、`null`、空串和空数组。MySQL `TIMESTAMP` 与 `DATETIME` 的时区行为不同，显式定义同步格式和会话时区。
- 多表组成一份文档时，要能从被修改的关联行找到受影响主键并重建；可回查源库、维护宽表或使用流处理状态，分别带来读压、维护或状态管理成本。
- 监控 CDC 延迟、积压、失败、位点和剩余 binlog 保留窗口。验收覆盖新增、更新、物理/逻辑删除、重复、乱序、暂停恢复和新索引切换；定期做数量及内容对账，保留重建操作手册。
